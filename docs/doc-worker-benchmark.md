# Document Worker 选型基准结论（qwen3:4b 第一轮）

日期：2026-08-16　|　状态：第一轮验证完成

## 1. 结论摘要

**qwen3:4b 通过首轮验证，可以作为本地文档 Worker 的默认模型进入试运行。**

三份模拟 PRD（智能温控器 / 48V BMS / 屏幕截图工具）跑完 A/B/C 三个任务：

| 任务 | Schema 合法 | 平均耗时 | 平均输出 | 质量评价 |
|------|:---:|:---:|:---:|------|
| A 纯提取 | 3/3 | ~14s | ~830 tok | 优秀：无编造，正确区分功能/非功能/验收/待确认 |
| B 需求分解 | 3/3 | ~47s | ~2700 tok | 良好：粒度合理，能识别文档歧义；1 处编造约束 |
| C 测试用例 | 3/3 | ~49s | ~2700 tok | 良好：边界/异常覆盖好；个别编造精度数值 |

## 2. 关键结论

1. **模型能力符合"机械初稿 + 主代理终审"定位**：A 任务完全可用；B/C 输出约 80% 可直接使用，剩余 20%（编造的具体数值、软约束被写死）需要 DeepSeek 审核时修正。
2. **速度可接受**：8K 上下文下模型 100% 在 GPU（RTX 4050 6GB），单文档单任务 12~77s。
3. **已知坑**：
   - qwen3 默认思考模式与 `format=json` 冲突（答案进 `thinking`、`response` 为空）。**必须带 `"think": false`**。
   - 模型偶发返回空数组（基准中 9 次出现 3 次，重跑均恢复）。服务器已加"主条目为空则整体重试一次"保护。
   - 16K 上下文时模型被挤到 CPU/GPU 混合（5.4GB > 6GB），明显变慢；8K 上下文 3.9GB 纯 GPU。长文档靠分块解决。

## 3. 基准方法

- 任务：A 纯提取（基线）/ B 需求分解 / C 测试用例生成。
- 工具：[doc_worker.py](../doc_worker.py)（FastMCP + Ollama），`format=json` + `think=false`，温度 A=0.2、B/C=0.4。
- 评测：`python scripts/doc_worker_bench.py`（遍历 `tests/fixtures/*.md`，输出到 `tests/bench_outputs/`）。
- 评审：`python scripts/review_bench_results.py`。
- Schema 合法率 + 耗时 + token 统计自动完成；内容质量人工逐条评审。

## 4. 下一步（待用户确认）

1. 用 1~3 份**真实 PRD** 复跑 A/B/C，验证对真实文档形态的表现。
2. 测量"DeepSeek 审核修复成本"：本地跑 + DeepSeek 审核 vs 全 DeepSeek 直接做，按总成本公式（云端 token 费用 + 本地推理时间 + 人工修正时间）定论——收益口径：同样任务完成质量下，本地方案云端 token 显著更少、耗时略长可接受。
3. 若 B/C 的编造问题在真实文档上更严重，再拉 qwen3:8b 做对照。
4. 试运行通过后，再考虑 CPU/GPU 并行、多任务流水线等优化（当前不做）。

## 5. 接入方式

- Trae：`mcp.json` 已加入 `doc-worker` 条目。
- Codex：在 `~/.codex/config.toml` 追加（需重启 Codex）：

```toml

command = "<python>"

startup_timeout_sec = 10

```

## 6. 真实文档验证（2026-08-16，私有 FOC 项目）

使用一个私有 FOC 学习仓库（只读，未改动任何文件）中的三份真实文档复测：

| 真实文档 | 任务 | 分块 | 耗时 | 输出 | 质量评价 |
|---|---|:---:|:---:|:---:|---|
| 项目状态与协作交接文档 | B 需求分解 | 3 | 114s | 5939 tok | 良好：忠实拆出 31 条，含硬约束与协作规则；但过度分解（环境配置也拆成需求），且 1 处编造约束（"30 分钟完成全流程"，原文无） |
| 学习总计划文档 | A 纯提取 | 4 | 52s | 2559 tok | 优秀：35 条任务覆盖五个阶段+文档约定+推送检查；跨分块有少量近似重复（去重未识别同义句） |
| 电机参数解读文档 | C 测试用例 | 2 | 53s | 2929 tok | 优秀：把"参数流水线"转化为参数一致性校验用例，覆盖缺口（单位换算、四舍五入、定点数逻辑）切中要害 |

### 6.1 真实场景结论

1. **多分块合并链路经受住真实长文档考验**（3~4 块跨块合并，含大量表格），无内容丢失、无 id 冲突。
2. **错误模式与模拟件一致且不更严重**：编造（1 处）、过度分解、跨块近似重复——均为"初稿可接受、主代理终审可修正"级别。
3. **测试用例任务是当前最强项**：能从技术笔记推导出可执行的验证步骤和精确的期望值。
4. 唯一需要在服务器侧补的：跨分块去重对"同义不同字"的句子失效，可在合并时按编辑距离做近似去重（当前未实现，已知限制）。

## 7. 第二轮：HTML+SVG 笔记重写（2026-08-16，结论：qwen3:4b 不适合）

以私有 FOC 学习仓库中的两份 HTML 学习笔记为靶，复现"重写笔记 + 用 SVG 绘图"的真实任务：

### 7.1 测试内容

- **D：电机原理笔记 6.4 节（SVPWM）重写**。输入为早期提交中的旧版 6.4 节（1004 字符），任务为扩写子章节并绘制"图20 矢量六边形"SVG。对照目标：人工修正后的当前版（29291 字符），其中 T0 定义与六扇区查表是历史纠错点。
- **E：硬件笔记"信号流框图"SVG 绘制**。输入为信号链路文字描述（MCU → 扩展接口 → 电机驱动模块 → 电机），任务为绘制完整框图 SVG。

### 7.2 结果与失败模式

| 尝试 | 结果 |
|---|---|
| think=False（默认） | 规划文字大量泄漏进输出（"首先，用户要求我…"），HTML/SVG 草稿与计划交织，8K token 预算被耗尽截断 |
| think=True | 思考过程耗尽 8K 输出预算，`response` 为空（与 JSON 模式同源） |
| think=False + 结构示例 + 禁止计划指令 | 仍以计划文字开头，无完整交付物 |
| 16K 上下文（想加大预算） | 模型被挤到 CPU/GPU 混合（5.4GB>6GB），300s 超时 |

### 7.3 结论与建议

1. **qwen3:4b 无法干净完成 HTML+SVG 长文重写**。失败点是"先规划、再一次性产出长结构化工件"的能力，这正是 4B 模型的短板，与提示词无关。
2. 这证实了分层原则的边界：**结构化抽取/分解/测试用例（JSON 短任务）适合本地 4B；长文 HTML+SVG 生成（高判断 + 长输出）应保留在云端 DeepSeek**。
3. 若想继续压低成本，两条路：
   - 用 **qwen3:8b** 单独对照本轮任务（5.2GB 可单独驻留 GPU），验证"规划纪律"是否随参数量改善；
   - 若坚持 4B，必须**把任务拆碎**：一次只生成一个小 SVG（几何参数由主代理显式给出），主代理负责组装整章。
